## 1. 组件与边界

~~~text
管理员浏览器
    │ HTTPS / 会话 Cookie
    ▼
Nginx ── Vue 3 + TypeScript 静态页面
    │ /api
    ▼
Spring Boot 3.5.x / JDK 21 / MyBatis ───── MySQL 8
    │  ▲            内容、配置、扫描状态、通知事件
    │  │ 内部 API
    ▼  │
Python 监控容器：1 个管理进程 + 每个启用 UP 1 个子进程
    │ B 站 API、飞书 Webhook
    ▼
外部服务
Spring 图片任务 ── B 站图片 ── 私有阿里云 OSS
~~~

Nginx 只公开 80/443；Spring 内部接口、MySQL 和 Python 进程仅在 Docker 私有网络可达。所有页面与内容 API（登录接口除外）使用同一个管理员会话。Spring 校验环境变量中的管理员密码哈希；无管理员数据表。内部 API 另用服务令牌鉴权，前端从不接触它。

## 2. UP 进程生命周期

Python 容器只有一套镜像。管理进程每 15 秒读取启用的 UP 清单，按 UID 确保恰好一个子进程；新增时启动，停用时请求其在当前安全点退出，异常退出时退避重启。子进程不通过命令行传 Cookie 或 Webhook，B 站 Cookie 来自环境变量，群路由由 Spring 的内部 API 提供。停用保留数据库内容和待发队列；重新启用先处理可发送队列，再扫描当时最新 50 条及固定目标。

每个子进程沿用现有脚本的增量审计思路：空间动态先取最多 50 条，再过滤充电专属文字/图片；专属路由对应的固定动态另外按详情获取。正常轮次开始间隔最短 15 秒，完整评论校准沿用现有 24 小时默认值。处理 API 失败与“成功返回空评论”必须严格区分；失败时不推进对应扫描进度。

## 3. 批次入库与通知入队

1. Python 获取外部数据并整理为有序的小批次。动态、根评论、楼中楼、图片元数据和新的飞书消息各有稳定来源 ID。
2. 子进程调用 Spring 内部批次接口。Spring 服务层以 `@Transactional` 包住同一数据源上的 MyBatis 写入，在**一次短 MySQL 事务**中幂等更新内容、更新该批扫描状态、按唯一事件键插入通知事件；三者全部成功才提交。单批建议至多 100 条评论，长扫描拆成多个批次，不能把整轮 B 站请求包进数据库事务。
3. 批次提交后才允许发送对应飞书事件。重试相同批次使用动态 ID、评论复合主键和事件去重键，不重复入库或入队。
4. 编辑覆盖已存内容，不生成新事件。确认来源不可用时只标记，不删除内容。图片上传状态由独立任务更新，不阻塞文字入库。

事务只涵盖 MySQL 写入。B 站请求、OSS 上传和飞书 HTTP 调用均在事务外。若飞书接收成功但确认结果未写回数据库，租约过期后会再次发送；系统选择至少一次投递，允许极少量重复。

## 4. 飞书出站队列

通知事件按所属 UP 与全局事件 ID 排序，目标角色为 ALL、UP 或 OPS。动态概览需要当前路由中所有非空评论群；普通评论只需 ALL；UP 本人评论需要 ALL 和 UP；运维事件只需该 UP 的 OPS。专属路由完全覆盖默认路由。服务端在认领待发目标时重新读取当前路由，故未发目标跟随配置变化；已成功目标固定在原群，不补发。已处理完成的旧事件不会因后来新增路由而重新打开。

每个目标单独记录尝试次数、下次重试时间、租约和实际群。动态与评论图片的飞书上传沿用现有脚本所需的飞书应用凭据，与站内 OSS 缓存独立。失败退避沿用现有脚本的 5、10、15、30、60 秒阶梯，之后封顶 60 秒；同一群较早待发目标未完成时，后续目标等待，以保持发送顺序。进程崩溃后租约过期可重新认领。已完成事件及投递记录保留 90 天，未完成记录不清理。

每个启用 UP 每小时向自己的运维群发送正常心跳；同一抓取错误连续发生时每轮都发错误通知。可归属某 UP 的进程崩溃由管理进程记录并尝试入队该 UP 的运维事件；无 UP 归属的数据库、反向代理等全局故障仅记服务器日志。若运维群本身不可达，保留失败状态并写日志。

## 5. 图片与来源状态

Spring 的图片任务异步读取 PENDING/RETRY 的动态和评论图片，校验来源地址，使用所需 B 站请求头/共享 Cookie 下载，再上传到私有 OSS 并记录 OSS Key。下载或上传暂时失败时按退避重试；来源确定不存在时标为 UNAVAILABLE，页面保留文字与占位提示。头像沿用来源链接，不进入 OSS。图片来源地址仅供服务端处理，不直接作为私有内容的前端回退地址。

前端使用鉴权后的图片接口；Spring 为 READY 图片生成短效 OSS GET 签名链接并重定向。实施设计的签名时长为 10 分钟，重载同一站内图片地址即可取得新签名。签名 URL 在有效期内可被持有人使用，因此只向登录会话发放，且不写入日志。

动态跌出最新 50 条不代表删除。固定目标详情明确不可用时可标记动态；评论只有在完整且成功的校准后才能确认缺失，分页失败不得标记删除。来源恢复时清除不可用标记，仍保留同一主键。

## 6. 安全与容量

- 飞书 Webhook 在 MySQL 中加密，密钥存环境变量；B 站 Cookie、管理员密码哈希、OSS 凭据和内部 API 令牌也只从服务器配置读取。公开 API 永不返回明文 Webhook 或 Cookie。
- 公开登录会话采用 HttpOnly、Secure、SameSite Cookie；修改配置的接口校验 CSRF。单实例会话可使用 Spring 内存会话，服务重启后重新登录。
- 初始 1～2 个 UP 可按进程隔离运行；UP 数增加会线性增加 Python 内存与 B 站请求量。部署前在目标 2 GB 机器上测量 MySQL、JVM、Nginx、图片任务和每个 Python 子进程的峰值，并以实际数据决定同时启用数量。
- 现有两份 Python 脚本是算法和消息格式的迁移参考。旧 JSON 状态、队列与路由不导入；正式切换先停旧监控，避免重复推送。
