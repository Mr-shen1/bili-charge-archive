# 产品需求文档（PRD）

- 版本：v1，2026-09-25
- 状态：需求已确认；产品尚未开发
- 目标用户：一位管理员，在手机和桌面浏览器上查看已保存的充电动态与评论，并管理 UP 和飞书通知配置
- 关联文档：[架构](ARCHITECTURE.md) · [数据库](DATABASE.md) · [接口](API.md) · [验收](ACCEPTANCE.md)

## 1. 背景与目标

现有 Python 脚本抓取 B 站充电动态和评论并发送飞书，尚无网站和持久化查询。新系统应把符合范围的内容保存到 MySQL，以接近 B 站动态的手机阅读方式展示，同时将飞书路由从配置文件迁至管理页面。

成功标准：管理员能按 UP 查动态、进入动态详情直接看评论；可管理多个 UP 及其飞书群；进程或外部服务出错后不丢失已确认的内容和待发通知；在现有 2 GB 阿里云主机上完成部署与容量验收。

## 2. 范围

### 包含

- 仅采集指定 UP 的**充电专属文字或图片动态**及其文字、图片评论；普通动态、视频等其他内容类型不入站。
- 每轮查看该 UP 空间**最新 50 条动态（先取 50 条，再筛选）**。为具体动态配置专属路由后，该动态成为固定目标，即使跌出最新 50 条也继续监控；仍须属于该 UP 且符合内容类型。
- 管理员登录后查看动态、评论和管理页。动态、评论只读。
- 动态与评论图片存入私有 OSS；UP/评论作者头像沿用来源图片链接。
- 飞书动态、评论、UP 运维通知及失败重试。

### 不包含

- 对最新 50 条之外的普通历史动态进行回填；UP 重新启用后也只检查当时最新 50 条和固定目标。
- 网站发动态、评论、回复、点赞；富文本表情和 @ 的特殊渲染；多管理员及公开访客访问。
- 导入旧脚本的 JSON 扫描状态、旧飞书队列或旧路由配置；保存 B 站接口完整原始 JSON。

## 3. 页面与操作

### 3.1 登录和导航

登录页是唯一无需会话即可访问的页面。登录后进入动态列表，导航提供动态、UP 管理、飞书群管理和退出。网站及图片访问接口均须鉴权。管理员凭据由服务器环境变量提供，不建设多用户管理页面。

### 3.2 动态列表

顶部以 UP 头像提供“全部 / 指定 UP”筛选。卡片展示 UP 信息、动态发布时间、可选标题、正文和图片预览、**本站实际保存的评论总数**。按动态发布时间倒序、动态 ID 倒序稳定排序，每页 20 条，有上一页/下一页。停用的 UP 的既有内容仍可查看，明确标示其监控已停用。点击卡片进入独立动态详情页，适配手机单列布局。

### 3.3 动态详情与评论

详情页先完整展示动态，评论直接显示在动态下方。根评论按发布时间倒序，每页 20 条；一条根评论下的楼中楼按发布时间正序，独立分页，实施设计每页 20 条。保留回复层级及被回复者关联。评论显示作者信息、文字、图片、时间；不提供互动按钮。

内容编辑时覆盖为最后一次成功抓到的版本，不保留编辑历史，也不另发飞书编辑通知。来源确认删除或不可访问时保留已存内容并显示“来源已不可用”；跌出最新 50 条本身不等于删除。已存评论数包含根评论、楼中楼及这些保留的评论。

图片尚未上传成功时先展示文字，在图片位置显示失败/加载中状态并后台重试；不得因为一张图片阻止整条内容显示。

### 3.4 飞书群管理

管理员先登记可复用的群名称与 Webhook，再在 UP 和动态路由中选择。列表不回显完整 Webhook；允许更新名称和 Webhook。实施设计：仍被 UP 运维、默认路由或专属路由引用的群不得删除，页面显示引用位置。Webhooks 只用于服务端发送。

### 3.5 UP 管理

列表显示头像、名称、UID、启停状态、最近成功扫描、最近错误及待发通知数。添加时接受 UID 或空间链接，先预览 UP 资料；保存前必须选择非空的运维群及至少一个默认评论群（全部评论群或 UP 群）。若两种评论群都选，必须是不同的群。新增 UP 默认启用并开始首次扫描。

可编辑分组并停用/重新启用 UP。停用立即停止新的采集与飞书发送，既有内容、配置和待发队列保留；重新启用后继续发送未完成通知，并只从当前最新 50 条及固定目标发现停用期间仍可访问的新内容。管理页展示自动重试状态，不设“立即重扫”或“手动重发”按钮，也不硬删除 UP。

### 3.6 具体动态路由

在所属 UP 下输入动态 ID 或链接，预览并验证作者与内容类型后，选择至少一个且互不相同的“全部评论群”和“UP 群”。专属路由对该动态**完全覆盖** UP 默认路由，并使其成为固定目标。删除专属路由后重新使用默认路由；若已不在最新 50 条则停止常规监控，但本站内容保留。

路由变更作用于之后发现的内容及**尚未发送成功**的待发目标；已发送成功的通知不撤回、不补发。给已入站动态新加专属路由，不重放以前已处理的动态或评论。

## 4. 抓取与通知规则

- 每个启用的 UP 正常轮次的开始间隔**最短 15 秒**；实际轮次可能更久。继续采用增量审计与定期完整校准，失败不把未完成的扫描误记为成功。
- 新 UP 的首次扫描会把最新 50 条中符合范围的现存动态及评论作为基线保存，**按有效路由将可投递的现存内容全部入飞书待发队列**，不静默跳过旧评论。若仅配置 UP 群，普通用户评论没有接收群，仍入站但不发飞书。固定目标首次发现时同理。
- 没有专属路由时使用该 UP 的默认评论群；有专属路由时只用专属路由。每个 UP 的运维群只接收该 UP 的心跳与故障；无 UP 归属的全局服务/数据库故障只记服务器日志。

| 事件 | 全部评论群已配置 | UP 群已配置 |
| --- | --- | --- |
| 新动态概览 | 发送 | 发送 |
| 普通用户评论/回复 | 发送 | 不发送 |
| UP 本人的评论/回复 | 发送 | 发送 |
| 每小时正常心跳、该 UP 故障 | 不发送 | 不发送，改发该 UP 运维群 |

同一种抓取错误连续发生时**每轮都通知**运维群。飞书失败按目标自动重试，并保持同一目标的发送顺序。优先避免漏发：若飞书已经接收，但进程在记录成功前崩溃，重试可能造成极少量重复。已成功的投递记录保留 90 天；待发或失败记录保留到处理完成。

## 5. 质量与部署约束

- 手机优先，桌面可用；页面查询、图片预览与管理操作须可在手机浏览器完成。
- 初始规模 1～2 个 UP，目标服务器为已有 Docker 的 2 GB 阿里云主机、固定公网 IP、无域名。正式部署前须实测服务总内存，不能只按估算承诺容量。
- 站点通过 HTTPS 访问；私有 OSS 图片仅向已登录用户发放短效访问链接。Cookie、管理员密码哈希、OSS 密钥、飞书加密密钥均不出现在前端或代码中。
- 新系统上线前停止旧监控，避免两套程序同时推送；新系统从空状态开始，旧状态不迁移。
